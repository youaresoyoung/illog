# 데이터 저장소 기능 정의서

## 1. 개요

앱의 모든 데이터를 **로컬 SQLite 데이터베이스**에 저장하는 기능입니다. 데이터베이스 초기화, 스키마 마이그레이션, 기본 데이터 시드, 소프트 삭제 정책을 포함합니다. 외부 서버로 사용자 데이터를 전송하지 않습니다.

## 2. 목적 및 사용자 가치

- 사용자의 기록을 전적으로 로컬 기기에만 보관해 프라이버시를 보장한다.
- 네트워크 없이도 앱의 모든 기능을 사용할 수 있게 한다.
- 앱 업데이트 시 기존 데이터를 잃지 않고 스키마를 갱신한다.

## 3. 저장소 구성

| 항목         | 값                                           |
| ------------ | -------------------------------------------- |
| 데이터베이스 | SQLite (`better-sqlite3`)                    |
| ORM          | Drizzle ORM                                  |
| 파일 위치    | Electron 사용자 데이터 디렉터리              |
| 파일 이름    | 환경 변수 `DB_FILE_NAME`                     |
| 접근 방식    | 동기(synchronous) — 메인 프로세스에서만 접근 |

- 렌더러는 데이터베이스에 직접 접근할 수 없으며, 반드시 IPC를 거친다.

## 4. 테이블 목록

| 테이블              | 용도                 | 소프트 삭제    |
| ------------------- | -------------------- | -------------- |
| `task`              | 로그                 | ✅             |
| `task_note`         | 로그 노트 (1:1)      | ❌ (연쇄 삭제) |
| `task_reflection`   | AI 회고 (1:1)        | ❌ (연쇄 삭제) |
| `task_tag`          | 로그-태그 연결 (N:M) | ❌ (연쇄 삭제) |
| `tag`               | 태그                 | ✅             |
| `project`           | 프로젝트             | ✅             |
| `task_type`         | 작업 유형            | ✅             |
| `task_subtype`      | 세부 유형            | ✅             |
| `weekly_reflection` | 주간 회고            | ❌             |
| `app_setting`       | 앱 설정 (키-값)      | ❌             |

### 4.1 관계도

```
project ──┐
          │ (N:1, CASCADE)
task_type ─┼── task ──┬── task_note        (1:1, CASCADE)
   │       │          ├── task_reflection  (1:1, CASCADE)
   │ (SET NULL)       └── task_tag ── tag  (N:M, CASCADE)
task_subtype ─┘

weekly_reflection   (독립)
app_setting         (독립)
```

## 5. 기능 상세

| ID       | 기능                | 설명                                                             |
| -------- | ------------------- | ---------------------------------------------------------------- |
| FR-DB-01 | 데이터베이스 열기   | 사용자 데이터 디렉터리에 데이터베이스 파일을 열거나 생성한다.    |
| FR-DB-02 | 스키마 마이그레이션 | 앱 시작 시 미적용 마이그레이션을 자동으로 실행한다.              |
| FR-DB-03 | 기본 데이터 시드    | 작업 유형 테이블이 비어 있으면 기본 유형과 세부 유형을 삽입한다. |
| FR-DB-04 | 소프트 삭제         | 주요 엔티티는 삭제 시각을 기록하는 방식으로 삭제한다.            |
| FR-DB-05 | 연쇄 삭제           | 로그가 물리 삭제되면 종속 데이터도 함께 삭제된다.                |
| FR-DB-06 | 앱 설정 저장        | 키-값 형태로 앱 설정을 저장·조회한다.                            |

### 5.1 앱 시작 시 초기화 순서

```
사용자 데이터 디렉터리 경로 확인
  → 데이터베이스 파일 열기 (없으면 생성)
  → Drizzle 인스턴스 생성 (스키마 바인딩)
  → 마이그레이션 폴더의 미적용 마이그레이션 실행
  → 기본 작업 유형 시드 (테이블이 비어 있을 때만)
  → 저장소/서비스 인스턴스 생성 및 IPC 핸들러 등록
```

## 6. 데이터 삭제 정책

| 방식        | 대상                                                  | 동작                                                                             |
| ----------- | ----------------------------------------------------- | -------------------------------------------------------------------------------- |
| 소프트 삭제 | `task`, `tag`, `project`, `task_type`, `task_subtype` | 삭제 시각 컬럼을 채운다. 모든 조회에서 삭제 시각이 비어 있는 행만 대상으로 한다. |
| 연쇄 삭제   | `task_note`, `task_reflection`, `task_tag`            | 부모 로그가 물리 삭제될 때 함께 삭제된다.                                        |
| 참조 해제   | `task.task_type_id`, `task.task_subtype_id`           | 참조 대상이 물리 삭제되면 `null`로 설정된다.                                     |
| 미지원      | 전체                                                  | 사용자에게 물리 삭제·휴지통·복구 수단을 제공하지 않는다.                         |

> 실제 운영에서는 소프트 삭제만 사용되므로 연쇄 삭제와 참조 해제는 거의 발동하지 않는다.

## 7. 타임스탬프 표기

테이블마다 타임스탬프 저장 형식이 다르다.

| 형식                         | 사용 테이블                                                                    |
| ---------------------------- | ------------------------------------------------------------------------------ |
| 정수 (Unix epoch 초)         | `task`, `tag`, `task_type`, `task_subtype`, `weekly_reflection`, `app_setting` |
| 텍스트 (`datetime` 문자열)   | `project`, `task_reflection`                                                   |
| 텍스트 (밀리초 epoch 문자열) | `task_note`                                                                    |

## 8. 비즈니스 규칙

| ID       | 규칙                                                                                                              |
| -------- | ----------------------------------------------------------------------------------------------------------------- |
| BR-DB-01 | 모든 사용자 데이터는 로컬에만 저장되며 외부로 전송되지 않는다.                                                    |
| BR-DB-02 | 마이그레이션은 앱 시작 시 자동 실행되며 사용자 개입이 없다.                                                       |
| BR-DB-03 | 시드는 작업 유형 테이블이 완전히 비어 있을 때만 실행된다.                                                         |
| BR-DB-04 | 데이터베이스 접근은 메인 프로세스로 제한된다.                                                                     |
| BR-DB-05 | 주요 엔티티의 이름 필드에는 유일성 제약이 걸려 있어, 삭제된 항목과 같은 이름으로 재생성하면 복구 동작이 발생한다. |
| BR-DB-06 | 조회 쿼리는 항상 삭제되지 않은 행만 대상으로 하며, 조인 시에도 삭제된 연관 항목을 제외한다.                       |

## 9. 개발 명령

`services/app` 디렉터리에서 실행한다.

| 명령               | 설명                                                                         |
| ------------------ | ---------------------------------------------------------------------------- |
| `pnpm db:generate` | 스키마 변경 사항으로부터 마이그레이션 파일을 생성한다                        |
| `pnpm db:migrate`  | 네이티브 모듈 재빌드 → 마이그레이션 적용 → Electron용 재빌드를 순차 수행한다 |
| `pnpm db:studio`   | 데이터베이스 브라우저를 실행한다                                             |

## 11. 현재 제한사항 및 향후 계획

- **백업·복원·내보내기 기능이 없다.** 사용자가 데이터를 다른 기기로 옮기려면 데이터베이스 파일을 직접 복사해야 한다.
- 클라우드 동기화(`sync.cloud`)는 기능 플래그만 정의되어 있고 구현이 없다.
- PDF 내보내기(`export.pdf`) 역시 플래그만 존재한다.
- 마이그레이션 실패 시 복구 절차나 사용자 안내가 없다.
- 소프트 삭제된 데이터를 정리하는 수단이 없어 데이터베이스가 계속 커진다.
- 데이터베이스 파일이 암호화되어 있지 않다.
- 타임스탬프 저장 형식이 테이블마다 달라 통일이 필요하다.
- 데이터베이스 파일 경로를 사용자가 변경할 수 없다.
