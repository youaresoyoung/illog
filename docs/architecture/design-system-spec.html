illog — Design System Spec 파이프라인

packages/ui의 컴포넌트 스펙 추출 파이프라인을 정리한 문서입니다. YAML로 쓴 컴포넌트 스펙을 읽어 검증하고, 디자인 토큰을 실제 값으로 해석해 문서용 표와 생성 파일로 만드는 흐름을 파일 단위 → 함수 단위 순으로 좁혀가며 보여줍니다. 진입점은 두 CLI 엔트리(pnpm spec:validate, pnpm spec:generate)입니다. 생성물 2개는 양쪽 모두 소비처에 연결된 상태입니다 — spec.json은 services/web의 문서 표가, spec.types.ts는 Button/types.ts가 실제로 import합니다. 현재 브랜치에 존재하는 코드만 반영했습니다. 앱 전체 구조는 아키텍처 다이어그램을 참고하세요.

1 파이프라인 전체 흐름

사람이 쓰는 입력은 컴포넌트 스펙(spec/*.yaml)과 그 형태를 규정하는 JSON Schema이고, 여기에 @illog/themes의 디자인 토큰이 합쳐집니다. 검사는 형식(JSON Schema) → 의미(코드) 2단계로 나뉘며, 형식 검사를 통과하지 못한 파일은 의미 검사로 넘어가지 않습니다. 파이프라인 중간 산출물(Issue[], ComponentSpec[], 표)을 두 CLI 엔트리가 각각 소비해, 한쪽은 종료 코드를 다른 한쪽은 커밋되는 생성 파일 2개를 내놓습니다. 그 두 파일은 각각 services/web의 문서 표와 Button/types.ts로 흘러들어가, YAML이 문서와 타입 양쪽의 SSOT가 됩니다.

생성 파일을 왜 커밋하는가 — generate.ts의 주석에 적힌 정책 그대로, codegen을 돌리지 않은 상태에서도 에디터와 typecheck가 동작해야 하기 때문입니다 (generatedColors.ts와 같은 방침). 현재 두 파일 모두 git에 추가돼 있고, .gitignore가 잡는 것은 dist뿐입니다.

두 생성물의 배치가 다른 이유 — spec.json은 전 컴포넌트를 하나로 모읍니다. 문서 사이트가 getComponentSpec(id)로 목록 전체를 한 번에 필요로 하기 때문입니다. 반대로 타입은 컴포넌트 폴더 안에 co-location합니다 — 컴포넌트를 지우면 생성물도 같이 사라집니다. 출력 위치는 id에서 추론하지 않고 스펙의 sourceDir 필드를 따르는데, Selector/TagSelector처럼 중첩된 컴포넌트가 있어 pascal(id) 규칙이 성립하지 않기 때문입니다.

2 모듈 의존 관계 (파일 단위)

각 파일이 scripts/spec 안에서 무엇을 import하는지 그대로 옮긴 그래프입니다(외부 패키지는 3절에서 다룹니다). 화살표는 위에서 아래 한 방향으로만 흐르며 순환이 없습니다 — 아래층 파일은 위층을 절대 import하지 않기 때문에, 어느 파일을 엔트리로 잡아도 초기화 순서 문제가 생기지 않습니다. types.ts와 utils.ts는 import가 하나도 없는 잎(leaf)이고, 모듈을 불러오는 것만으로 무언가 실행되는 파일은 L4 두 개뿐입니다 — 나머지는 전부 함수만 내보냅니다.

왜 단방향이 중요한가 — 이전 구조에서는 lib.ts가 checkSemantics.ts를 부르고 checkSemantics.ts가 다시 lib.ts의 토큰 해석 함수를 불러 순환이 있었습니다. 함수 선언이 호이스팅되는 덕에 우연히 동작했을 뿐, 화살표 함수로 바꾸거나 CJS로 번들하면 바로 깨지는 상태였습니다. 토큰 해석을 resolveToken.ts로 내리면서 순환이 사라졌습니다.

3 함수 호출 흐름 (함수 단위)

각 함수가 어디서 호출되는지를 그린 콜 그래프입니다. 실선은 실제 호출, 점선은 아직 호출부가 없는 것(예정)입니다. 두 CLI 엔트리 모두 loadSpecs() 하나로 시작하고, generate.ts만 표 생성까지 내려갑니다. flattenDefinitions와 tryResolveTokenRef가 검사 경로와 표 생성 경로 양쪽에서 공유되는 점이 이 구조의 핵심입니다 — definitions의 4중 중첩을 순회하는 코드가 한 곳에만 존재합니다.

4 함수별 역할 정리

위 콜 그래프의 각 노드가 실제로 무슨 일을 하고, 무엇을 돌려주는지 한 줄로 정리했습니다.

파일 함수 역할 반환
validate.ts top-level loadSpecs() 결과를 아이콘과 함께 출력하고 집계. error가 있거나 --strict에서 warn이 있으면 exit(1) 종료 코드
generate.ts top-level error가 하나라도 있으면 생성하지 않고 중단 → 모든 sourceDir이 실재하는지 확인 → 통과하면 spec.json 1개와 컴포넌트별 spec.types.ts를 쓴다. sourceDir이 없거나 variants가 없는 스펙은 건너뛰고 이유를 출력한다 spec.json + 타입 파일 N개
generate.ts sourceDir 사전 검증 파일을 하나라도 쓰기 전에 전 스펙의 sourceDir을 existsSync로 확인. mkdir -p가 오타 경로에 빈 폴더를 조용히 만드는 것을 막는다 통과 또는 exit(1)
generate.ts writeFile(path, content) 디렉터리 생성 → 파일 쓰기 → prettier 포맷. 포맷 실패는 경고만 하고 넘어간다 void
generate.ts pascal(specId) -/_로 끊어 PascalCase로. 타입 이름 ButtonVariant를 만드는 데만 쓰인다 — 출력 경로는 sourceDir에서 온다 string
loadSpecs.ts loadSpecs(specDir?) yaml 파일 나열 → 파싱 → JSON Schema 형식 검사 → id/파일명 일치·중복 확인 → checkSemantics 위임 LoadResult
loadSpecs.ts getValidator(path) ajv 컴파일 결과를 경로별로 캐시 (import 시점이 아닌 첫 호출 때 1회) ValidateFunction
loadSpecs.ts schemaPathFor(dir) 스펙 디렉터리로부터 스키마 경로를 만든다 (픽스처 디렉터리 지원) string
checkSemantics.ts checkSemantics(spec, file) 형식 검사를 통과한 스펙의 의미를 검사 — 선언되지 않은 variant/값/state/element 참조, 해석 불가 토큰, 스타일 미구현 등 Issue[]
flattenDefinitions.ts flattenDefinitions(spec) selector → state → element → property 4중 중첩을 평평한 항목으로 편다. 검사와 표 생성이 이 순회 하나를 공유한다 Generator<DefinitionEntry>
flattenDefinitions.ts parseSelector(selector) selector 문법을 해석하는 유일한 곳. 'size=md' → [{ variant, value }], 'base' → [] SelectorPart[]
flattenDefinitions.ts describeLocation(entry) 이슈 메시지와 에러가 공유하는 위치 표기를 만든다 string
resolveToken.ts tryResolveTokenRef(ref) $color/$size/$text 참조를 실제 값으로 해석. 실패를 예외가 아닌 값으로 돌려주므로 호출부가 Issue로 모을 수 있다 TokenResolution
resolveToken.ts getColorKeyMap() generatedColors의 var(--x) → camelCase 키 역색인. 첫 호출에만 만들고 이후 재사용 Map<string, string>
buildTables.ts buildPropsTable(spec) variants와 props를 합쳐 문서 props 표의 행을 만든다 PropRow[]
buildTables.ts buildSpecTable(spec) definitions를 해석된 값이 담긴 행으로 펼친다. 해석 실패 시 위치를 붙여 던진다 SpecRow[]
utils.ts toKebab · getIn · quote · formatDefault 도메인 지식이 전혀 없는 순수 헬퍼. 스펙·토큰·파일 구조를 알아야 하면 이 파일이 아니다 —

5 두 CLI 엔트리의 실행 분기

같은 loadSpecs()에서 출발하지만 error를 다루는 방식이 다릅니다. validate는 전부 출력하고 종료 코드로 알리는 리포터이고, generate는 error가 하나라도 있으면 생성물을 손대지 않고 중단합니다 — 깨진 스펙이 커밋되는 파일로 새어나가지 않게 하는 장치입니다. warn은 양쪽 모두 통과시키되, validate --strict에서만 실패로 취급합니다.

현재 실제 실행 결과 — pnpm spec:validate는 error 0 · warn 3으로 exit 0, --strict를 붙이면 exit 1입니다. pnpm spec:generate는 spec.json 1개, 타입 파일 1개 (컴포넌트 1개, 타입 3개)를 생성하며, 다시 돌려도 결과가 바뀌지 않습니다(idempotent).

중단 지점이 두 개인 이유 — 첫 번째(error)는 스펙 내용이 깨진 경우고, 두 번째(sourceDir)는 스펙과 실제 파일 구조가 어긋난 경우입니다. 후자를 별도 단계로 앞세운 것은 writeFile이 mkdirSync(recursive)를 하기 때문입니다 — 경로에 오타가 있으면 검증 없이는 컴포넌트도 없는 빈 __generated__ 폴더가 조용히 생겨납니다. 그래서 첫 파일을 쓰기 전에 전 스펙을 먼저 훑습니다.

6 생성물 2개와 그 소비처

generate.ts가 만드는 두 파일은 성격이 다릅니다 — 하나는 기계용 통합 스펙, 하나는 타입 전용입니다. 둘 다 git에 커밋해서, codegen을 돌리지 않은 상태에서도 에디터와 typecheck가 동작하게 합니다. 두 경로 모두 소비처까지 연결됐습니다 — spec.json은 package.json의 exports에 서브패스로 올라가 문서 사이트가 import하고, spec.types.ts는 같은 폴더의 types.ts가 import합니다. YAML을 고치고 spec:generate를 돌리면 문서 표와 컴포넌트 타입이 함께 따라옵니다.
