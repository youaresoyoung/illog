illog — CI/CD 아키텍처

.github/workflows의 워크플로우 4개와 컴포지트 액션, 그리고 services/app/forge.config.ts의 서명·배포 설정을 직접 읽어 그린 다이어그램입니다. 트리거 맵 → 일상 CI → 재사용 검증 → 릴리스 파이프라인 → 배포/자동 업데이트 순으로 범위를 좁혀갑니다. 앱 내부 구조는 아키텍처 다이어그램을 참고하세요.

1 트리거 → 워크플로우 맵

어떤 Git 이벤트가 어떤 워크플로우를 깨우는지, 그리고 그 워크플로우들이 공유하는 두 가지 재사용 단위(reusable-validate.yml 재사용 워크플로우, setup-node-pnpm 컴포지트 액션)를 보여줍니다. 브랜치가 develop → release/* → main → tag로 승격될수록 검증 강도와 배포 범위가 넓어집니다.

2 일상 CI 파이프라인 (ci.yml)

PR과 develop/staging push에서 도는 단일 잡입니다. 핵심은 nx affected — nrwl/nx-set-shas가 base/head SHA를 계산해주고, 그 범위에 영향을 받는 프로젝트에 대해서만 lint·typecheck·test·build를 재실행합니다. 포맷 검사만 예외적으로 저장소 전체(prettier --check .)를 훑습니다.

3 재사용 검증 워크플로우 (reusable-validate.yml)

릴리스 계열 워크플로우 3개가 공유하는 workflow_call 워크플로우입니다. 일상 CI와 달리 affected가 아니라 run-many로 전 프로젝트를 검증하고, 테스트 대신 illog-app:build(렌더러 빌드)까지 확인합니다. extract-version 입력이 켜지면 태그명 또는 루트 package.json에서 버전을 뽑아 version·is_prerelease 출력으로 호출자에게 돌려줍니다.

4 태그 릴리스 파이프라인 (tag.yml)

v* 태그 push에서만 도는 실제 배포 경로입니다. macOS 러너에서 임시 키체인을 만들어 인증서를 넣고 electron-forge publish로 빌드 → 서명 → 공증 → S3 업로드를 한 번에 처리한 뒤, 서명/공증 결과를 codesign·spctl·stapler로 되짚어 검증합니다. arm64와 x64를 순차로 돌리기 때문에 두 번째 빌드가 out/make를 덮어쓰지 않도록 중간에 아티팩트를 백업·복원하는 단계가 끼어 있습니다.

6 워크플로우 비교

네 워크플로우가 어디까지 책임지는지 한눈에 비교한 표입니다. S3/CloudFront 배포와 GitHub Release 생성은 오직 tag.yml만 수행하며, main.yml과 release-checks.yml은 서명된 산출물을 GitHub Actions 아티팩트로만 남깁니다.

문서와 실제 설정의 차이: release-checks.yml의 요약 스텝은 "Notarization will be done on main branch"라고 적고 있지만, forge.config.ts의 osxNotarize는 APPLE_ID와 APPLE_ID_PASSWORD가 모두 있으면 활성화됩니다. 세 macOS 워크플로우 모두 두 값을 주입하므로 실제로는 release 브랜치에서도 공증이 수행됩니다. 실제로 갈리는 지점은 공증 여부가 아니라 make(로컬 산출물)와 publish(S3 업로드) 중 무엇을 쓰느냐입니다.
