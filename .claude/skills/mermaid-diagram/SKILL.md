# Mermaid Diagram

프로젝트 아키텍처를 여러 장의 Mermaid 다이어그램으로 그려 브라우저에 띄우는
스킬입니다. "아키텍처를 보여줘", "구조 다이어그램 만들어줘", "이 프로젝트 의존성
시각화해줘" 같은 요청에서 사용하세요.

**이 스킬에는 분석 스크립트가 없습니다 — 정규식으로 디렉터리를 훑어 자동으로
그리면 품질이 떨어집니다** (중첩된 `src` 구조에서 전체가 노드 하나로 뭉개지거나,
`export default Foo` 같은 흔한 패턴을 놓치는 등). 실제로 사람이 아키텍처
다이어그램을 그릴 때처럼, Read/Grep/Bash로 코드를 직접 읽고 이해한 내용을
바탕으로 다이어그램을 손으로 작성하세요. 아래는 그 과정을 순서대로 정리한
체크리스트입니다.

## 진행 순서

### 1. 진입점부터 읽는다

디렉터리 목록을 훑지 말고 실제 시작점을 찾아 여세요: 프론트엔드라면
`main.tsx`/`index.tsx`(그리고 그게 렌더링하는 `App.tsx`), 백엔드/Electron
메인 프로세스라면 `main/index.ts` 같은 파일입니다. `find`/`ls`로 후보를 좁힌
뒤 Read로 내용을 확인하세요.

### 2. 실제 import를 따라간다 (추측 금지)

페이지 → 컴포넌트 → 훅으로 이어지는 관계는 각 파일을 Read로 열어 import 문을
직접 확인하세요. "이 파일을 누가 쓰는지"가 궁금하면 `grep -rl "importName"`으로
역방향도 확인합니다. 짐작으로 엣지를 그리면 안 됩니다 — 실제로 import되지 않은
관계를 그리면 다이어그램이 거짓말을 하게 됩니다.

### 3. 아키텍처 계층을 코드의 실제 패턴으로 알아챈다

디렉터리 이름이 아니라 코드가 실제로 어떻게 쓰였는지로 역할을 판단하세요:

- 클래스 이름이 `*Repository`/`*Service`로 끝나는가?
- 여러 Repository/Service를 `new`로 만들어 핸들러 등록 함수에 넘기는 "조립
  지점(composition root)" 파일이 있는가? (예: `registerHandlers.ts`,
  `bootstrap.ts`, `container.ts`) 있다면 그 파일을 Read로 통째로 읽고, 어떤
  변수가 어떤 클래스의 인스턴스이며 어디로 전달되는지 손으로 추적하세요.
- `create(...)`로 만들어진 Zustand류 스토어, `createContext(...)`로 만들어진
  React Context가 있는가? 있다면 grep으로 실제 사용 지점을 모두 찾으세요.
- `useQuery`/`useMutation`/`useSWR` 같은 서버 상태 훅이 있는가?

### 4. 범위를 좁혀가는 여러 장의 다이어그램으로 나눈다

한 장에 모든 것을 욱여넣지 마세요. 발견한 패턴에 맞춰 아래처럼 나누는 것이
보통 잘 맞습니다 (해당 패턴이 없는 계층은 건너뛰세요 — 억지로 채우지 않습니다):

1. **시스템 개요** — 프로세스/패키지/서비스 경계 (예: Electron의
   Main/Preload/Renderer, 모노레포의 워크스페이스 패키지들)
2. **백엔드 계층 구조** — Repository → Service → Handler/Controller가
   실제로 어떻게 연결되는지 (2번 단계에서 추적한 그대로)
3. **컴포넌트 트리** — 진입점에서 시작해 실제로 도달 가능한 페이지/컴포넌트/
   훅. 디렉터리로 뭉치지 말고 **컴포넌트/함수/파일 단위**로 노드를 그리세요.
4. **상태 흐름도** — 스토어/Context 정의 → 실제로 그것을 호출하는
   컴포넌트/훅. 서버 상태(React Query 등)가 있으면 별도로 구분하세요.

### 5. HTML로 작성하고 스타일링한다

Write 도구로 `docs/architecture/index.html`을 직접 작성하세요 (기존 파일이
있으면 먼저 Read). 다음을 지키면 결과물이 훨씬 읽기 좋아집니다:

- `<script src="https://cdn.jsdelivr.net/npm/mermaid@10/dist/mermaid.min.js">`로
  Mermaid.js를 불러오고, `mermaid.initialize({ startOnLoad: true, theme: "dark" })`
  로 초기화
- 다크 테마: 배경 `#1a1a1a`, 다이어그램 컨테이너는 살짝 밝은 `#212121`~`#232323`
- 각 다이어그램 섹션마다: 번호가 붙은 제목, **이 다이어그램이 무엇을 보여주는지
  1~2문장 설명**, 필요하면 색상 범례, 그리고 `<div class="mermaid">...</div>`
- Mermaid `classDef`/`class`로 역할별 색을 통일하세요 (예: 페이지는 파란색,
  컴포넌트는 초록색, 훅은 보라색, 스토어는 stadium 모양 `(["label"])`, Context는
  육각형 `{{"label"}}`, 외부 브릿지/DB는 실린더 `[("label")]`) — 도형과 색이
  일관되면 범례 없이도 노드 종류가 구분됩니다.
- 노드가 너무 많아 한 다이어그램이 지저분해지면 `subgraph`로 역할별/계층별로
  묶으세요.

### 6. 브라우저로 연다

```bash
open docs/architecture/index.html          # macOS
xdg-open docs/architecture/index.html       # Linux
```

## 완료 보고

다 되면 다음과 같이 짧게 보고하세요:

> 아키텍처 다이어그램이 브라우저에서 열렸습니다.

어떤 다이어그램을 그렸는지(예: "시스템 개요, 백엔드 계층, 컴포넌트 트리,
상태 흐름도 4장을 그렸습니다") 한 줄 덧붙이면 유용하지만, 장황한 설명은
피하세요.

## 주의

- 큰 프로젝트를 통째로 열어보려 하면 컨텍스트가 금방 찹니다. 진입점에서 시작해
  필요한 파일만 따라가며 읽고, 이미 확인한 관계는 다시 읽지 마세요.
- 확실하지 않은 관계는 그리지 말고, 확인이 필요하면 사용자에게 "이 부분은
  범위를 좁혀서 볼까요?"라고 물어보세요.
- 재실행하면 `docs/architecture/index.html`을 덮어씁니다.
